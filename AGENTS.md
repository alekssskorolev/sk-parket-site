# Работа с проектом через оркестратора

Главный агент каждого чата в этом проекте — оркестратор. Пользователь общается с ним; специализированные субагенты выполняют отдельные этапы и возвращают результаты оркестратору. Назначенный субагент исполняет свою роль и не запускает новую цепочку оркестрации.

## Начало задачи

1. Прочитай `docs/AI_HANDOFF.md`. Проверь действующие инструкции, рабочую папку, наличие checkout, ветку, SHA и незакоммиченные изменения. Не стирай чужую работу. Если исходников нет локально, получи доступный checkout через разрешённые инструменты; наличие только документации не означает наличие проекта целиком.
2. Определи режим: основной облачный сайт, SQLite-сервер или старое демо. Через карту функций и diff относительно базового SHA исследуй затронутый код и его связи. При расхождении руководства с кодом проверяй код.
3. Определи ожидаемый результат и проверки. Спрашивай только при существенной неоднозначности или недостающем доступе; обычные решения принимай самостоятельно.

## Роли

| Роль | Инструкция | Ответственность |
| --- | --- | --- |
| Оркестратор (основной чат) | Этот файл | Понять запрос, определить объём и полномочия, назначить этапы, проверить результаты, довести задачу до завершения и ответить пользователю |
| Сопоставление материалов | `agents/material-matcher.md` | По необходимости перед разработкой: сравнить заданные материалы админки с магазином, вернуть подтверждённые и спорные соответствия; только чтение |
| Разработчик сайта | `agents/site-developer.md` | Изучить код, реализовать изменение, собрать generated-файлы, выполнить проверки; передать результат без публикации |
| Редактор руководства | `agents/handoff-editor.md` | Точечно обновить только `docs/AI_HANDOFF.md`, когда изменились описанные в нём сведения |
| Агент выпуска | `agents/release-manager.md` | Опубликовать проверенный кандидат в пределах полномочий, дождаться CI/развёртывания, проверить фактический результат |

Файлы `agents/*.md` — задания ролям, которые оркестратор явно передаёт запускаемым субагентам. Они сами по себе не создают постоянно работающих агентов и не регистрируют роли в настройках клиента. Специализация обеспечивается чтением актуального руководства, кода и результата предыдущего этапа, а не предположением о памяти прошлого субагента.

## Последовательность

Если для синхронизации ещё нет проверенных соответствий товаров, сначала запусти агента сопоставления для нужных материалов и магазина. Однозначные результаты передай разработчику, существенные неоднозначности уточни у пользователя. При готовых актуальных соответствиях этот этап пропусти.

1. Для изменения сайта запусти субагента-разработчика с инструкцией прочитать свой файл роли. Передай запрос, режим, checkout/ветку, исходный SHA, критерии готовности, ограничения и чужие изменения, которых нельзя касаться.
2. Дождись результата. Проверь итоговый diff, соответствие запросу и доказательства проверок. Недостатки верни разработчику; не принимай отметку «готово» без проверки. Дополнительного независимого проверяющего привлекай для существенных изменений расчёта, данных, API или авторизации; он только читает код и сообщает замечания.
3. Реши, требуется ли актуализация handoff: точки входа, связи компонентов, функции, API/модель, права, env, source/generated связи, команды или выпуск. При необходимости запусти редактора руководства с итоговым diff и результатами проверок. Замена текста или стиля без изменения описанных связей этого не требует. Дождись результата и проверь его. Необходимая документация должна входить в тот же кандидат выпуска.
4. Только после завершения кода, проверок и документации передай агенту выпуска кандидат, объём разрешённой публикации и способ проверки. Оркестратор организует подготовку окончательного коммита в рабочей ветке после актуализации документации; коммит содержит только согласованные изменения. Перед публикацией зафиксируй точный SHA кандидата (включая документацию) и предыдущую версию. При незакоммиченных изменениях кандидат ещё не готов к выпуску. Не меняй его параллельно с выпуском.
5. Дождись подтверждённого выпуска. Если CI или smoke-проверки не прошли, верни диагностику разработчику, затем повтори необходимые проверки и актуализацию документа для нового кандидата. Успешный push или старт workflow не означает успешную публикацию. При неудаче оцени доступный совместимый откат в пределах полномочий; откат кода не откатывает данные.
6. Ответ пользователю даёт только оркестратор: что изменилось, чем проверено, опубликовано ли, ссылка на результат/commit при наличии, ограничения. При блокировке явно отдели готовые локальные изменения от работающего сайта и назови причину.

Для вопросов без правок достаточно ответа оркестратора. Для задач только о документации запускай редактора с нужным объёмом, пропуская разработку приложения и выпуск, если публикация не запрошена. Не создавай субагентов ради формального прохождения этапов.

Экономь контекст: передавай роли конкретный участок задачи и нужные ссылки/разделы, не всю переписку. Читай только инструкцию назначенной роли. Возвращай краткий результат и доказательства, без дублирования исходников и логов; для исследования без правок достаточно таблицы и ограничений.

## Передача результатов и совместная работа

- Отчёт роли: исходный/текущий SHA или незакоммиченный статус; изменённые файлы; что и почему изменено; выполненные проверки с результатами; что не проверено; риски; что требуется следующей роли. Для выпуска — кандидат, CI run/status, фактическая версия/URL и smoke-результат.
- Оркестратор запускает и координирует субагентов; роли не создают других агентов и не назначают друг другу задачи. Можно продолжить работу существующего субагента, но передать актуальные данные обязательно.
- Записи выполняются последовательно: разработчик → редактор руководства → агент выпуска. Не допускай одновременного редактирования одних файлов. Другие чаты могут работать независимо: проверяй ветку/HEAD перед передачей и выпуском.
- Область файлов роли — рабочая инструкция, не техническая защита: субагенты имеют общую файловую систему и унаследованные разрешения.
- Если субагенты недоступны, сообщи пользователю и выполни этапы последовательно самостоятельно с теми же проверками. Не имитируй запуск агентов и не оставляй работу незавершённой только из-за их отсутствия.

## Полномочия и правила проекта

- По согласованному с владельцем процессу обычный запрос внести изменение на сайт включает стандартную публикацию проверенного изменения существующим способом. Если пользователь просит только анализ, черновик, локальную правку, подготовку PR или запрещает публикацию, не публикуй. В задаче настройки этих инструкций публикация не требуется.
- Это не разрешение менять рабочие данные, выполнять миграции production, менять секреты/IAM/домен/инфраструктуру, обходить защиту веток или делать force push. Необходимость таких действий сначала выяви и подготовь конкретный план; запроси недостающие полномочия только на фактический следующий шаг.
- Доступы получай через подключения или авторизованную консоль. Не проси секреты в чат, не помещай их и клиентские записи в задания/документацию/логи.
- Меняй исходники, generated-файлы обновляй штатной сборкой. Не используй `build:demo` для рабочего облачного сайта. Не считай `npm start` эквивалентом облачного runtime.
- Проверки выбирай по handoff и реальному diff. Не изменяй зависимости, чтобы скрыть несовместимость платформы; сообщай о невыполненных проверках. Не запускай рабочие POST, тестовые заявки, отправку уведомлений или публикацию контента админки как неявный smoke-test.
- `docs/**` запускает cloud-deploy workflow при push в `main`: обновление handoff тоже может выпустить новую версию функции и Pages. Агент выпуска учитывает этот эффект и обратную совместимость API/страницы/данных. Публикация инструкции не является условием её применения в текущем локальном проекте.
